Reflection on the Enhancement Process

One of the biggest things I learned during this enhancement was the difference between making an application work and designing an application to remain manageable as it grows. When I originally developed the software, my primary focus was implementing the functionality the clinic needed and getting a working MVP ready for testing. As more functionality was added, the main application file continued to grow and eventually contained API routes, database operations, business logic, validation, and error handling in the same file. Although the application worked, revisiting it for this enhancement made it much easier to see how difficult that structure would become to maintain as the software continued to expand.

The biggest challenge was refactoring a working application without changing or breaking its existing behavior. Instead of rewriting the backend all at once, I separated it incrementally and tested the application after each major change. I first separated configuration and database functionality, followed by the Pydantic models and API routers, and then moved more complex operations into service modules. This process taught me the importance of making smaller, testable changes during refactoring rather than attempting a large restructuring at once.

I also gained a better understanding of how validation and error handling contribute to both software quality and security. For example, I added validation that prevents an injection dose from being zero or negative and verified that FastAPI rejects the request with a 422 response before it reaches the database. I also changed expected application conditions, such as requesting an injection record that does not exist, to return an appropriate 404 response. Unexpected exceptions are now handled centrally and return a generic response instead of exposing internal error details.

Feedback on my original enhancement plan specifically supported the proposed architectural refactoring through modularization and separation of concerns and did not identify any required changes. I therefore continued with the planned approach while using incremental testing to validate the refactoring and preserve the application's existing behavior.

Overall, this enhancement helped me look at the application less as a collection of working features and more as a software system that needs to be maintainable, secure, testable, and capable of continued growth.

Category Two: Algorithms and Data Structures

First Expired, First Out (FEFO) Inventory Allocation

For the Algorithms and Data Structures enhancement, I improved the inventory management process within the Orelia Clinic Management Software by implementing a First Expired, First Out (FEFO) allocation algorithm. The enhancement automatically prioritizes eligible medication inventory based on expiration date, helping ensure that inventory expiring soonest is used before newer inventory.

The algorithm retrieves eligible, non-expired inventory lots in expiration-date order and performs a linear traversal to determine how the required medication quantity should be allocated. When a single lot cannot satisfy the requested amount, the algorithm continues across multiple lots until the required quantity has been fulfilled. A new relational allocation structure also preserves the exact inventory lots and quantities associated with each injection.

Enhancement Highlights

  • Implemented FEFO inventory allocation based on medication expiration dates
  • Added expiration-date tracking to inventory records
  • Added linear traversal of ordered inventory lots to fulfill medication requirements
  • Supports allocation across multiple inventory lots
  • Records exact lot-by-lot inventory usage for each injection
  • Added transactional inventory deductions and restoration
  • Updated injection creation, modification, and deletion to support FEFO allocations
  • Preserved backward compatibility with injection records created before the enhancement
  • Added insufficient-inventory handling with 409 Conflict responses
  • Prevents partial inventory deductions when an allocation cannot be fulfilled
  • Improved data integrity and traceability through a one-to-many injection-to-allocation relationship

This enhancement demonstrates the use of algorithmic principles to solve a practical inventory-management problem while improving the reliability, traceability, and scalability of the original application.

Enhancement Narrative

Artifact Description

The artifact I selected for my Algorithms and Data Structures enhancement is my Wellness Clinic Management Software, an independently developed full-stack application that I originally began creating in March 2026 for a local wellness clinic. The application was designed to replace manual record-keeping processes with a digital system that manages patients, medications, inventory, injections, payments, laboratory information, treatments, and other clinic operations. An MVP of the application was completed and ready for beta testing in May 2026.

For this milestone, my main focus was improving the way the application manages medication inventory when injections are recorded. The original implementation required an individual inventory lot to be selected and deducted inventory from that single lot. Although this worked for the initial version of the application, it did not account for expiration dates or situations where the required quantity needed to be fulfilled from multiple inventory lots. I enhanced this functionality by implementing a First Expired, First Out (FEFO) inventory allocation process that prioritizes eligible medication lots according to expiration date.

Justification for Inclusion and Enhancement

I chose this artifact for my ePortfolio because it demonstrates how algorithms and data structures can be applied to solve a practical problem within a real software application. Medication inventory is well suited for this type of enhancement because simply knowing how much inventory is available is not enough. The application also needs to determine which inventory should be used first and how a requested quantity should be allocated when multiple lots are available.

The enhanced implementation first retrieves eligible inventory lots that have available quantities, valid expiration dates, and have not expired. PostgreSQL orders these records by expiration date so that the inventory expiring soonest is considered first. The application then performs a linear traversal of the ordered inventory lots, allocating the required quantity from each lot until the medication requirement has been satisfied. If one lot does not contain enough inventory, the algorithm continues to the next eligible lot. This allows a single injection to be fulfilled using multiple inventory lots when necessary.

I also expanded the underlying data structure supporting the algorithm. I added expiration-date information to inventory records and created a one-to-many relationship between an injection and its inventory allocations. Instead of storing only one lot number with an injection, the application can now preserve the exact inventory lots and quantities used to fulfill it. This improves traceability while allowing the FEFO algorithm to operate across multiple inventory records.

The enhancement also required changes to the complete injection lifecycle. Injection creation now calculates and records FEFO allocations, while updates restore the previous allocation before recalculating inventory requirements. Deleting an injection restores the exact quantities to the inventory lots from which they were originally deducted. These operations are performed transactionally so that an error does not leave inventory in a partially modified state.

Testing demonstrated that the algorithm correctly prioritized the earliest-expiring eligible inventory, allocated medication across multiple lots, restored inventory during updates and deletions, and rejected requests when the combined eligible inventory could not satisfy the required quantity. For insufficient inventory, the application returns a 409 Conflict response without performing a partial deduction.

Course Outcome Coverage

This enhancement met the course outcomes I originally planned to address, particularly the outcome related to designing and evaluating computing solutions using algorithmic principles while considering trade-offs. Implementing FEFO required me to determine how inventory should be filtered, ordered by expiration date, and traversed to allocate the required quantity across one or more lots.

The enhancement also demonstrates the use of well-founded computing techniques to provide value within a specific industry. FEFO improves medication inventory management by prioritizing inventory that expires sooner while maintaining accurate allocation records and transactional integrity. My original outcome-coverage plan did not change, and this enhancement strengthened the evidence for the outcomes I intended Category Two to address.

Course Outcomes One, Two, and Five were not the primary focus of this enhancement and are demonstrated through other components of the capstone and ePortfolio.

Reflection on the Enhancement Process

One of the biggest things I learned from this enhancement is that implementing an algorithm in an existing application involves more than writing the algorithm itself. FEFO initially seemed straightforward by prioritizing inventory by expiration date and then using the earliest expiring inventory first. However, integrating it into the application required me to consider how the algorithm would affect inventory records, injection history, updates, deletions, and existing data.

One of the main challenges was moving from the original design, where an injection was associated with a single inventory lot, to supporting allocations across multiple lots. Creating a separate allocation structure allowed the application to preserve exactly which lots and quantities were used. I also had to ensure that updating or deleting an injection correctly restored those allocations. This gave me a better understanding of how algorithms, data structures, and database relationships work together within a larger application.

Testing was also an important part of the learning process. I created controlled inventory lots with different expiration dates and quantities and tested multi-lot allocation, updates, deletions, and insufficient inventory. These tests helped me identify integration issues and verify that transactions prevented partial database changes when an operation failed.

Feedback on my original enhancement plan supported the use of FEFO as a practical inventory-allocation strategy and recognized how the algorithm could support operational decision-making. No changes to the planned enhancement were required, so I continued with the proposed FEFO approach while refining its integration through testing.

Overall, this enhancement strengthened my understanding of algorithmic problem-solving and showed me the importance of considering how an algorithm affects the entire application rather than viewing it as an isolated piece of code.

Category Three

Databases

Database Performance, Integrity, and Scalability

For the Databases enhancement, I improved the PostgreSQL database used by the Orelia Clinic Management Software by focusing on query performance, data integrity, and scalability. The enhancements were based on the application's existing database operations and the ways clinic data is retrieved and maintained.

Targeted database indexes were added to support FEFO inventory queries, chronological injection-history retrieval, and inventory allocation lookups. I also added a database-level constraint to prevent negative inventory quantities and implemented pagination for injection history so the application can retrieve manageable portions of data as the number of records grows.

Enhancement Highlights

  • Added a composite index on medication name and expiration date to support FEFO inventory queries
  • Added an index to support chronological injection-history retrieval
  • Added an index for efficient injection inventory-allocation lookups
  • Added a database-level constraint preventing negative inventory quantities
  • Validated the inventory constraint by confirming PostgreSQL rejects invalid negative quantities
  • Added LIMIT and OFFSET pagination to injection-history retrieval
  • Exposed pagination controls through the FastAPI endpoint
  • Improved database performance, integrity, reliability, and scalability

This enhancement demonstrates how database design decisions can improve the overall reliability and scalability of an application. Rather than changing the database unnecessarily, the enhancements target actual query patterns and data-integrity requirements within the clinic management system.
